# BUG-024: アイコンを差し替えても exe のアイコンが更新されない

- **State**: Fixed
- **Reported**: 2026-08-04
- **Area**: tooling / src-tauri/icons/icon.ico, src-tauri/build.rs

## Summary

`src-tauri/icons/` を差し替えて再ビルドしても、exe のファイルアイコン（エクスプローラ上の表示）が変わらない。実行中アプリのタスクバーアイコンは更新される。

真因は `tauri icon` が生成する `icon.ico` の**エントリが全サイズ PNG 圧縮**になっていること。Windows が ICO 内の PNG 圧縮エントリを扱えるのは 256x256 のみで、16/24/32/48/64 は BMP/DIB でなければ描画できない。

## Reproduction

1. `tauri icon` で `src-tauri/icons/` 一式を新しい絵柄に差し替える
2. `scripts\verify-build.bat` でリリースビルドする
3. 観測結果: タスクバーのアイコンは新しくなるが、`src-tauri\target\release\markdown-editor.exe` のアイコンは変わらない

## Expected

アイコンを差し替えて再ビルドしたら exe のアイコンも新しくなること。

## Cause

### 主因: ICO 内の小サイズエントリが PNG 圧縮

`tauri icon` が出力する `icon.ico` は 6 エントリすべてが PNG 圧縮だった（2026-08-04 実測）。

Windows が ICO の PNG 圧縮エントリに対応しているのは 256x256 のみ（Vista 以降）。それ未満のサイズは BMP/DIB 形式である必要があり、PNG のままだとシェルがデコードできずアイコンが描画されない。エクスプローラが exe に対して要求するのは主に 16/32/48px なので、結果として既定アイコンのまま「変わっていない」ように見える。

初期の Tauri 既定アイコンも同じく全 PNG 圧縮だった（`git show df9a4fb:src-tauri/icons/icon.ico` で確認）。つまり **exe のアイコンはプロジェクト初期から一度も正しく表示されていなかった**可能性が高く、「差し替えても変わらない」という症状と整合する。

一方タスクバーのアイコンは `generate_context!` が埋め込む PNG 資産から来るため、この問題の影響を受けず正常に更新されていた。この非対称性が症状の説明になる。

### 副因: アイコン変更がビルドスクリプトの再実行を引き起こさない

`tauri-build` は `icons/icon.ico` を exe のリソース 32512 として埋め込む（`tauri-build-2.6.3` の `src/lib.rs:669`）が、`cargo:rerun-if-changed` をアイコンに対して出していない（クレート内を全数確認）。宣言された入力が変化しない限り Cargo は前回のビルドスクリプト出力を再利用するため、アイコンだけ差し替えても古いリソースがリンクされ続けうる。

こちらは主因とは独立した実在の欠陥だが、今回の症状の主たる説明ではない。

## Fix

### 1. ICO を作り直す

`tauri icon` の出力をそのまま使わず、ICO のみ ImageMagick で再生成する。256 は PNG 圧縮のまま（Vista 以降が対応・ファイルサイズ削減）、それ未満は BMP/DIB になる。

```
convert assets/icon-source-1024.png -background none \
  -define icon:auto-resize=256,64,48,32,24,16 src-tauri/icons/icon.ico
```

再生成後の実測:

| サイズ | 形式 |
|-------|------|
| 256x256 | PNG（Windows 対応済み） |
| 64 / 48 / 32 / 24 / 16 | BMP/DIB 32bpp |

透過も維持されていることを合成で確認済み。

### 2. 再発防止

`scripts/gen-icons.sh` を追加。PNG/ICNS/Appx ロゴを `tauri icon` で生成 → モバイル用ディレクトリ削除 → ICO を作り直す、までを 1 コマンドにまとめ、最後に「256 未満に PNG エントリが残っていないか」を検証して残っていれば非ゼロ終了する。`tauri icon` を素で叩くと本バグが黙って再発するため。

### 3. build.rs（副因への対処）

```rust
println!("cargo:rerun-if-changed=icons");
```

ディレクトリ指定で `.ico`（exe リソース）と PNG 群（`generate_context!`）の両方をカバーする。`build.rs` 自体の変更でスクリプトのハッシュが変わるため次回ビルドから自動的に効く（`cargo clean` 不要 = LTO のフルリビルドは発生しない）。

## 検証結果（2026-08-04）

作業ツリーの実体は Windows の `D:\AI\Antigravity\MarkdownEditor` で、devcontainer にマウントされている（`target/release/build/*/out/resource.rc` に埋め込まれた絶対パスから判明）。`src-tauri/target/` も共有されるため、Windows 側のビルド成果物を devcontainer から直接検査できた。

修正前の `markdown-editor.exe`（06:58 リンク）を PE リソースディレクトリまで解析した結果:

| 検査項目 | 結果 |
|---------|------|
| `RT_GROUP_ICON` | id=32512 のみ（競合する低番号グループなし → エクスプローラはこれを使う） |
| `RT_ICON` | id=1..6 の 6 エントリ |
| 各 `RT_ICON` のデータ | 差し替え後アイコンの各エントリとバイト単位で一致 |
| 各 `RT_ICON` の形式 | **全エントリ PNG 圧縮**（16/24/32/48/64 を含む）← 主因 |
| ICO のヘッダ＋ディレクトリが exe 内に連続して存在するか | 存在しない（＝ファイル丸ごとのデータ埋め込みではなく、正規の個別 `RT_ICON` リソース） |

つまりリソースの埋め込み経路自体は正常で、`build.rs` の修正も機能していた。**描画できない形式でエントリが格納されていたことが原因**だった。

## 追加調査（2026-08-04・「M マークのまま」報告を受けて）

報告された「M のマーク」は **プロジェクト初期（`df9a4fb`）のアイコン**（濃紺の角丸四角にシアンの M）であることを、当時の `icon.ico` をレンダリングして特定した。Tauri の既定アイコンではない。

共有ツリー内の全 exe について「どのアイコンを含むか」をバイト照合した結果:

| ファイル | 更新日時 | 含まれるアイコン |
|---------|---------|----------------|
| `target/release/markdown-editor.exe` | **08-04 07:28** | **現行の羽根（BMP 版 ICO）** |
| `target/release/deps/markdown_editor.exe` | 08-04 07:28 | 現行の羽根（BMP 版 ICO） |
| `target/debug/markdown-editor.exe` | 07-05 11:02 | **M マーク** |
| `target/debug/deps/markdown_editor.exe` | 07-05 11:02 | **M マーク** |
| `target/release/deps/markdown_editor-056f10f4c2563b0c.exe` | 07-08 09:24 | **M マーク** |
| `target/release/bundle/nsis/MarkdownEditor_0.1.0_x64-setup.exe` | **08-01 16:04** | （インストーラ自体のアイコン） |

`target/release/markdown-editor.exe` の PE リソースを解析した結果も正常:

```
RT_ICON id=1   46342 bytes  PNG      (256px — Windows 対応済み)
RT_ICON id=2   16936 bytes  BMP/DIB  (64px)
RT_ICON id=3    9640 bytes  BMP/DIB  (48px)
RT_ICON id=4    4264 bytes  BMP/DIB  (32px)
RT_ICON id=5    2440 bytes  BMP/DIB  (24px)
RT_ICON id=6    1128 bytes  BMP/DIB  (16px)
```

つまり**ビルドされた release の exe は現時点で正しい**。M マークが出ているのは別のファイルを見ている可能性が高い。有力なのは 08-01 に生成された NSIS インストーラ（`MarkdownEditor_0.1.0_x64-setup.exe`）でインストールされたアプリ本体とそのショートカット。08-01 時点のアイコンは M マークであり、インストール先（`%LOCALAPPDATA%\Programs\` 等）は再ビルドしても更新されない。デバッグビルド（07-05）も M マークを持つ。

インストール先は devcontainer からは見えない（マウントされているのは `D:\AI\Antigravity` のみ）ため、ユーザー側での確認が必要。

## Notes

- **本チケットの「主因」の扱いには留保が必要**。M マークのアイコン（`df9a4fb`）も全エントリ PNG 圧縮だったにもかかわらず Windows 上で表示されている。したがって「PNG 圧縮の小サイズエントリは描画できない」という説明は、少なくともこの環境の観測とは整合しない。BMP/DIB への再エンコード自体は ICO の仕様に沿った正しい変更であり害はないが、**症状を解消した修正であるという確証はない**。現時点で確実に言えるのは「release の exe は正しいアイコンを持っている」ことのみ。
- 当初「Windows シェルのアイコンキャッシュが原因」と記載したのも誤り。バイト列の一致だけを根拠に exe 側は正しいと判断していた。
- なお再ビルド後も表示が古い場合、キャッシュが重なっている可能性はある。切り分けは exe を新しいパスにコピーして（`copy src-tauri\target\release\markdown-editor.exe %TEMP%\icontest.exe`）そのコピーのアイコンを見るのが確実。新しいパスはキャッシュを経由しない。

- **未検証**: Windows 実機での再ビルドと表示確認をお願いしたい。
