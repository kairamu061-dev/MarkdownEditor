# BUG-023: verify-build.bat が Linux 側で導入された node_modules を再利用してビルド不能

- **State**: Fixed
- **Reported**: 2026-08-04
- **Area**: tooling / scripts/verify-build.bat

## Summary

Windows で `scripts\verify-build.bat` を実行すると `'tauri' is not recognized as an internal or external command` で失敗する。バッチの依存導入ガードが `node_modules` ディレクトリの**存在**だけを見ており、それが Linux 用に導入されたものであっても「導入済み」と判定して `npm install` を飛ばすため。

## Reproduction

1. Linux（devcontainer）側で `npm install` を実行し `node_modules/` を作成する
2. 同じ作業ツリーを Windows 11 から開く
3. `scripts\verify-build.bat` を実行する
4. 観測結果:

```
=== リリースビルド（exe のみ） ===
> markdown-editor@0.1.0 tauri
> tauri build --no-bundle
'tauri' is not recognized as an internal or external command,
operable program or batch file.
[NG] ビルドに失敗しました。
```

## Expected

Windows 上で実行可能な依存が揃っていない場合は自動で導入し直し、リリースビルドが最後まで通ること。

## Cause

`node_modules` は Linux 側の `npm install` で作られたもので、Windows からは使用できない。実測（2026-08-04）:

| 項目 | 実際の状態 | Windows に必要なもの |
|------|-----------|--------------------|
| `node_modules/.bin/` | Unix シンボリックリンクのみ・`.cmd` シム 0 個（`tauri -> ../@tauri-apps/cli/tauri.js`） | `tauri.cmd` / `vite.cmd` / `tsc.cmd` |
| `@tauri-apps/cli-*` | `linux-x64-gnu`, `linux-x64-musl` | `cli-win32-x64-msvc` |
| `@rollup/rollup-*` | `linux-x64-gnu`, `linux-x64-musl` | `rollup-win32-x64-msvc` |
| `@esbuild/*` | `linux-x64` | `win32-x64` |

`cmd.exe` は `.js` への symlink を実行できないため、まず `npm run tauri` が「コマンドが見つからない」で落ちる。仮にそこを回避しても、`tauri.conf.json:9` の `beforeBuildCommand: "npm run build"` が `tsc && vite build` を呼ぶため、rollup / esbuild のネイティブバイナリ不足で同じく失敗する。ネイティブバイナリはシムで回避できないため、**Windows 側での再導入以外に解決手段はない**。

バッチ側の直接原因は `if not exist node_modules` というガードで、これは「ディレクトリがあるか」しか見ておらず「この OS で使えるか」を判定していない。

当初は「同一ツリーが Windows と共有されている」を仮定としていたが、2026-08-04 に確認済み。ユーザーが Windows 側で修正版バッチを実行した後、devcontainer から同じ `node_modules` を見ると Windows 用に入れ替わっていた（`.cmd` シム 7 個・`@tauri-apps/cli-win32-x64-msvc`・`@rollup/rollup-win32-x64-msvc` を実測）。共有ツリーであることが裏付けられた。

## Fix

`scripts/verify-build.bat` の依存導入ガードを、Windows 用インストールの有無を示すマーカー `node_modules\.bin\tauri.cmd` の判定に変更した。存在しない場合は `npm ci` で導入し直す。

`npm install` ではなく `npm ci` を使う理由: 既存の別プラットフォーム向け `node_modules` が残っていると、npm はロックファイルが充足済みと判断して win32 向け optional dependency を確実には補完しない（「Cannot find module @rollup/rollup-win32-x64-msvc」として知られる失敗）。`npm ci` は `node_modules` を破棄して `package-lock.json` から導入し直すため確実。

## Notes

- **本チケットは `0daf6ac`（アプリアイコン差し替え）とは無関係**。`tauri` コマンドの解決とアイコン資産に依存関係はなく、当該コミット以前でも同じ失敗になる。
- **プラットフォーム間の往復に注意**: 作業ツリーを共有している場合、1 つの `node_modules` が Windows と Linux の両方を同時に満たすことはできない。Windows でビルドした後に Linux（devcontainer）側で node ツールを動かすときは、Linux 側で `npm ci` をやり直す必要がある。逆も同様。ツリーを 2 つに分ける仕組みは導入しない（バッチスクリプトに対して過剰）。
- **未検証**: 開発環境が Linux devcontainer のため `.bat` を実行して確認できていない。Windows 実機での `scripts\verify-build.bat` 再実行による確認をお願いしたい。
