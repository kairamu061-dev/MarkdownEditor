# editor/tabs 開発メモ

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| 分割しない（タブバー UI とタブの並び・セッション保持を 1 つのサブ項目・1 ファイル `tabs.ts` に置く） | spec 直後の分割検討で、分かれ目の候補は「タブバー（UI）」と「タブの並び（データ）」。ただし並びは永続化もしない UI の内部状態で、バーは並び無しでは何も描けず、並びはバー無しでは操作する手段が無い。片方だけ切り出しても単独で検証できる意味を持たない。コードも約 200 行・1 ファイルで、6 文書を 2 組持つと文書がコードを大きく上回る（agent-rules の code-highlight の反省） |
| 同じノートを複数のタブで開かない（Obsidian からの意図的な差分） | タブごとに独立した `EditorState` を持つため、同じファイルを 2 つのタブで開くと互いの保存で上書きし合う |
| 新しいタブは中クリックと右クリックメニュー。Ctrl+クリックは使わない | ツリーの Ctrl+クリックは multi-select の選択切り替えに使用済み。ユーザ確認のうえ、既存操作を変えない案を採用（2026-11-23） |
| スクラッチ文書はタブにしない（タブ 0 個 = スクラッチ） | `currentPath === null` = スクラッチという既存の意味（自動保存・inline-title・削除）をそのまま使える。ユーザから「実装都合でよい」と回答あり |
| 切り替え・閉じる前の保存に失敗したら操作を止める | `pendingContent` は書き込み先のパスを持たない。止めずに切り替えると、未保存分が失われるか別のノートへ書かれる。リネーム・移動の既存の扱い（「保存できていないため〜できません」）に揃えた |
| 保管庫切り替えの前にも保存を確定する | 従来は確定しておらず、debounce 中の入力は `currentPath` が null になった時点で黙って捨てられていた。タブの全閉じと同じ手順に乗せるついでに塞ぐ |

## 発生した問題と対処

| 問題 | 対処 |
|------|------|
| spec の初稿は「入力欄で編集中に Ctrl+W を押すと先に blur で確定する」と書いていたが、実際は keydown で blur は起きず、inline-title の再描画で入力が黙って捨てられる | 入力欄（`HTMLInputElement`）にフォーカスがあるときはタブのキー操作を無視する。spec と E-09 を合わせて修正 |
| Ctrl+S はスクラッチ（`currentPath === null`）でも `pendingContent` を立て、`flushSave` はそれを消さずに戻る。従来は `openNote` が読み込み後に `pendingContent = null` で上書きして隠れていたが、`settleSave` で止める作りにした結果、以後の切り替えがすべて止まるようになった（レビューで発見） | `settleSave` の先頭で、スクラッチなら `pendingContent` を捨てて確定済みとする。不変条件の判定を 1 箇所に置くため、Ctrl+S 側ではなくここで扱う。E-19 を追加 |
| × で閉じるとフォーカスが × ボタンに移り、ボタンは再描画で消えるため、続く入力がどこにも入らない | `closeTab` の最後で `editor.focus()` |
| `openNote` は読み込み → 置き換えの間に await があり、待つ間の入力が次のノートのパスで保存されうる | 読み込みを先に済ませ、`settleSave` → 同期の置き換え、の順に固定（design の不変条件）。`settleSave` は確定中の入力に備えて最大 2 回確定する |

## 設計からの変更点

| 変更内容 | 理由 |
|----------|------|
| スクロール位置の退避を `scrollTop`（px）から `view.scrollSnapshot()` に変更（BUG-038） | `setState` 直後は見えていない行の高さが推定値で、px で戻すと実測との差だけずれた（Windows で最大 28px、headless では数百 px）。スナップショットは行位置基準なので推定値の影響を受けない。rAF での遅延も不要になった |
| タブを縮めない（`flex: none`）（BUG-040） | あふれたときに 80px まで縮み、日本語名が 3 文字ほどしか見えなかった。横スクロールがあるので縮める必要がない。最小幅 80px は残す — 一度外したら 1 文字の名前のタブの中央が × に当たり、クリックで閉じるようになった（BUG-041） |
| スクロールのスナップショットを次のフレームでもう一度当てる（BUG-038 の残り） | Windows で 51 回中 3 回、19px ずれが残った。headless で、見出し（推定 22px・実測 31px）が先頭に掛かっていると 1 回目の位置が推定の高さで決まり、差が残ることを確認。2 回目は実測済みの高さで合わせ直す。最初の実装は `view.state === session.state` で当て直しを判定していたが、直前の dispatch で state が作り直されるため常に偽で、当て直しが走っていなかった（doc の比較に変更） |
| タブバーで `scrollbar-width` を使わない（BUG-039） | Chromium は標準プロパティを指定すると `::-webkit-scrollbar` の装飾を無視し、OS 標準の見た目に戻す。全体の配色に任せ、`.tab-bar::-webkit-scrollbar` で太さだけ 6px にした |

## 今後の課題

- コンテナ内では esbuild + playwright のハーネスで確認した。tabs.ts 単体（スクロール・undo の保持、キー操作、remap、全閉じ）に加え、`@tauri-apps/api/core` と `/window` をメモリ上の偽物に差し替えて実際の `main.ts` を動かし、E-01/03/04/05/07/10/11/14/19 と保存失敗時の切り替え停止・再保存後の復帰を通した。WebView2 固有の挙動（中クリックの自動スクロール等）と実ファイルでの保存は Windows の確認に委ねる
- スクロール位置が小数（タッチパッド・高精度ホイール）で見出しを含む文書のとき、切り替えて戻ると最大 1px の差が出ることがある（方向はばらばら、Windows で 37 回中 9 回）。行の高さの端数の丸めと見られ、目では分からないため対応しない（BUG-038）
- 再起動時のタブ復元（settings に開いていたパスの一覧を保存する形になる）
- タブのドラッグ並べ替え・タブの右クリックメニュー（他を閉じる 等）
- 裏のタブはアプリ外での変更を反映しない（外部変更の検知そのものが未実装）
