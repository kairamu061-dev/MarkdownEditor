# file-explorer/multi-select 開発メモ

## 実装上の判断

| 判断内容 | 理由 |
|----------|------|
| サブ項目にした（2026-10-23） | 分割の例外は「追加ファイル 1 つ・独自 UI なし・独自スキーマなし」のすべてを満たす場合だけ。新規ファイルは selection.ts 1 つだが、範囲選択の四角と選択ハイライトという独自の UI 面を持つので例外に当たらない。範囲選択とまとめて移動はさらに分けていない — まとめて移動は選択が無いと検証できず、コードもおおむね 1 ファイルのため |
| 範囲選択は名前以外の場所から始める（2026-10-23・ユーザー選択） | 行全体が `draggable` で、行の上のドラッグはすでに移動に使われている。「エクスプローラー式（名前 = 移動、名前の右の空白・余白 = 範囲選択）」「選択状態で切り替え」「修飾キー + ドラッグ」の 3 案を示し、ユーザーがエクスプローラー式を選んだ。従来の単体移動の操作が変わらない |
| 選択できるのはノートだけ | 要望が「複数のノート」。フォルダを含めると「フォルダとその中のノートを同時に選んで移動」の重複処理が要る |
| 選択色にテーマ変数を足さない | 新しい変数は settings/theme の定義・theme-io の書き出し項目・テストケースに波及する。`color-mix()` で `--accent` から作れば、どのテーマでもアクセント色に追従する |

## 発生した問題と対処

| 問題 | 対処 |
|------|------|
| 余白のクリックでリネームが確定しなくなっていた | 範囲選択の mousedown で `preventDefault()` するとフォーカスが動かず、file-ops のリネーム入力が blur しない（blur で確定する・BUG-016）。入力欄そのものは範囲選択の対象外にし、それ以外の場所を押したときは container 内のフォーカスを明示的に外すようにした。headless で、余白クリックで `rename_path` が呼ばれることを確認 |
| 一部同名のときのステータスが 2 行に折り返した | 「N 件は移動先に同名の項目があるため移動しませんでした」を「同名の項目があるため N 件は移動しませんでした」に縮めた（spec も更新） |

## 設計からの変更点

| 変更内容 | 理由 |
|----------|------|
| 保存待ちの確定は、開いているノートが移動対象のときだけにした（未保存が残れば移動しない） | 当初は無条件に `flushPendingSave()` としていたが、関係のないノートの移動で保存を待つ理由がない。保存に失敗したまま移すと旧パスに未保存分が残るので、`renameCurrentNote` と同じく移動を止める。design.md を更新済み |

## 今後の課題

- リネーム入力欄の**中**をクリックすると、その場でリネームが確定する。クリックが行の click ハンドラまで伝わってノートを開き直すため。multi-select 以前（`d0c02ce`）から同じ挙動で、この変更による退行ではない。直すなら file-ops 側で入力欄の click の伝播を止める

- Shift + クリックの連続選択・一括削除は未対応（spec の未対応ケース参照）
